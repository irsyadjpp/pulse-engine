# 7. Document Development Guidelines

## 7.1 Document Creation Checklist

### BRD (Business Requirements Document)

- [ ] Purpose clearly defined
- [ ] Business scope documented (in/out of scope)
- [ ] AS-IS process described
- [ ] TO-BE process described
- [ ] Stakeholders identified
- [ ] Business requirements BR-XXX defined
- [ ] Business rules documented
- [ ] Data requirements specified
- [ ] Reporting requirements defined
- [ ] NFRs specified
- [ ] Assumptions, constraints, risks documented
- [ ] Success criteria defined

### FSD (Functional Specification Document)

- [ ] Maps to BRD
- [ ] Functional modules identified
- [ ] Actors defined
- [ ] Requirement mapping BR to module
- [ ] Consumer systems identified
- [ ] Functional assumptions documented
- [ ] Constraints specified
- [ ] Success criteria defined

### TSD (Technical Specification Document)

- [ ] Technology stack specified
- [ ] Architecture principles defined
- [ ] Architectural decisions documented (ADR)
- [ ] High-level architecture diagrammed
- [ ] System responsibilities clear
- [ ] Design principles stated
- [ ] Technical objectives defined
- [ ] Design constraints listed
- [ ] Technical risks identified
- [ ] Traceability principle established

## 7.2 Document Review Checklist

- [ ] Aligns with Product Vision
- [ ] Aligns with Business Architecture
- [ ] Traceable to BRD
- [ ] No scope creep
- [ ] Technical feasibility verified
- [ ] Security considerations addressed
- [ ] Compliance requirements met
- [ ] NFRs specified
- [ ] Review by relevant stakeholders
- [ ] Approval obtained

# 11. Documentation Best Practices

## 11.1 Writing Guidelines

* Use clear, concise language.
* Avoid jargon unless defined in glossary.
* Use consistent terminology across documents.
* Include examples where helpful.
* Use diagrams untuk complex concepts.
* Keep documents focused dan scoped.
* Update table of contents untuk long documents.

## 11.2 Diagram Guidelines

* Use Mermaid diagrams untuk consistency.
* Include diagram title dan description.
* Keep diagrams simple dan readable.
* Use consistent notation (C4 model, UML, etc.).
* Include source untuk generated diagrams.

## 11.3 Review Process

1. **Author Review** - Document completeness
2. **Peer Review** - Technical accuracy
3. **Stakeholder Review** - Business alignment
4. **Architecture Review** - Architectural compliance
5. **Security Review** - Security considerations
6. **Final Approval** - Document Owner

## D. Version Control

Semua dokumen harus menggunakan version control dengan format:

```
Version: Major.Minor.Patch
```

* **Major:** Structural changes, scope changes
* **Minor:** New sections, significant updates
* **Patch:** Typo fixes, clarifications

Setiap dokumen harus mencantumkan:

* Version number
* Last updated date
* Author/Owner
* Status
* Change history (summary)
